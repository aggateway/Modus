**MAJOR — Breaking Change**
A release is MAJOR when any previously VALID code is no longer usable for new reporting without consumer action. This means: a VALID code is marked SUPERSEDED (even with a supersession target provided), a VALID code is marked RETIRED with no replacement, or a VALID code's analyte identity changes such that historical results labeled with it are no longer correctly interpreted. The defining test is whether a lab or system that had a working integration yesterday needs to do something — update a code reference, remap historical data, or find an alternative method — after the release. The supersession file mitigates the disruption but does not eliminate the breaking nature of the change; it provides a migration path.

**MINOR — Revision**
A release is MINOR when it adds new content and nothing that was VALID before the release loses that status. New VALID method codes for existing or new analytes and restoration of a wrongly-retired code from RETIRED back to VALID all qualify. A consumer whose system queries all VALID codes will get more results after a MINOR release, but every result they were getting before will still be there. The practical implication for implementers is that their validation logic and enum lists may need updating to handle new codes, but no existing workflow breaks.

**PATCH — Clarification**
A release is PATCH when only descriptive or administrative metadata changes — controlled vocabulary corrections, clearing an incorrect change comment, or correcting a date field. No code is added, removed, or changes status. A consumer querying any method code before and after a PATCH release gets back the same method; only the human-readable description of that method may differ. The practical test: the diff touches only non-identity columns (not Method Code, Analyte Code, Status, or Extraction/Measurement fields) and the row count is unchanged.
